# KielTech Academy

KielTech Academy is a React/Vite learning portal served by an Express server. AI-powered features and Gemini integration are disabled.

## Run Locally

**Prerequisites:** Node.js

1. Install dependencies: `npm install`
2. Start the development server: `npm run dev`

## Firebase Hosting

The app uses Firebase Authentication and Cloud Firestore. Firebase Hosting serves the static Vite build; it does not run the Express server.

1. Install dependencies: `npm install`
2. Sign in to Firebase CLI: `npx firebase-tools login`
3. Build the site: `npm run build`
4. Deploy the site and Firestore rules to the configured `kieltech` project: `npx firebase-tools deploy --only hosting,firestore:rules`

The Hosting configuration publishes `dist`, routes client-side URLs to `index.html`, and applies cache headers to built assets. Review `firestore.rules` before deploying; they restrict student access to the student's own records, allow administrators to read student and learning records, and deny all other paths by default. No Gemini API key or AI service is required.

For local development, run `npm run dev`. For a standalone Express deployment, `npm start` serves the build from `dist`.

## Custom Authentication Emails (Local Express API)

Email/password registration sends a verification link through your SMTP server and requires verification before sign-in. Password-reset links are also generated by Firebase Admin and delivered through SMTP. Google sign-in continues to use Firebase Authentication directly.

Firebase Hosting serves only the static site and does not run the Express email API. This setup is available during local development and on a standalone Node.js deployment; to use it on the hosted site, deploy the Express server to a Node host that permits SMTP connections and route `/api/auth/email-action` to it. Firebase Functions are not required for the local setup.

For local setup:

1. Copy `.env.example` to `.env` and set the Gmail/Google Workspace sender and SMTP app password. With Gmail, enable 2-Step Verification, create an app password, and use that value for `SMTP_PASS`; do not use your normal account password.
2. Place a Firebase service-account JSON file at the path set by `GOOGLE_APPLICATION_CREDENTIALS`. Keep it private and do not commit it. The server uses it only to verify Firebase ID tokens and generate password-reset and email-verification links.
3. Confirm the site URL in `AUTH_CONTINUE_URL` is an authorized domain in Firebase Authentication. Configure Firebase's email action handler/templates as needed; the generated secure links are delivered using your SMTP sender.
4. Run `npm run dev` and test registration and password reset. The public reset endpoint returns a generic response whether or not an account exists.

Keep all SMTP credentials and Firebase Admin credentials on the server. Never add them to frontend environment variables or browser code. A production backend host still needs those values entered as private environment secrets.

## Reviewed Curriculum Refresh

The GitHub Actions workflow in `.github/workflows/curriculum-refresh.yml` checks one trusted official source for each of the ten courses on January 1 and July 1 (09:00 UTC). It can also be started manually from the repository's **Actions** tab. A check records source metadata and a content fingerprint only; it does not copy external lesson text, edit courses, publish lessons, or change exam questions. The first check records a baseline, and later source changes create review proposals in Firestore. All ten source checks must complete for the workflow job to succeed.

To enable the scheduled workflow without Firebase Cloud Functions:

1. Push this project to the default branch of a GitHub repository and ensure GitHub Actions is enabled.
2. Create a dedicated Google Cloud service account for the `kieltech` project and grant it only the **Cloud Datastore User** (`roles/datastore.user`) role needed to read and write the curriculum monitor/proposal documents.
3. Create a JSON key for that service account, then add its entire JSON content as a GitHub repository Actions secret named `FIREBASE_SERVICE_ACCOUNT`. Do not commit the key or paste it into source files, workflow logs, or chat. Rotate or revoke the key if it is ever exposed.
4. Open **Actions → Curriculum source refresh → Run workflow** to run and verify the first job. Scheduled runs will then execute in January and July.

GitHub-hosted runner usage is free for public repositories; private repositories use the free Actions minutes included in their GitHub plan. This workflow does not deploy or invoke Firebase Functions. The existing admin page's manual refresh and publish/reject operations still use Firebase callable Functions and will not work until those backend callables are deployed or replaced by a separate authenticated backend. An administrator reviews each proposal, writes original teaching content (overview, prerequisites, basics, progressive lessons with two explained examples each, advanced and extra topics, source reference, and a lesson-based knowledge check), then explicitly publishes or rejects it. Only published updates appear to authenticated students. These supplementary knowledge checks do not modify official assessment scores. Existing course stages, student progress, and official exams remain unchanged.

## Admin Operations Dashboard

An account with effective `admin` or `owner` role sees the **Admin** button in the header. The dashboard provides recent student profiles, synced course progress, assessment outcomes, and a timeline of selected learning and account events; the Curriculum review button opens the existing proposal workflow. Owners also have a **Manage admins** control. Reports are capped at 250 records per category. Assessment history and progress are read from the existing per-user `results` and `progress` subcollections.

The activity timeline records sign-ins, account creation and sign-outs, course and stage selections, assessment starts and submissions, and lesson bookmark changes. It is academic telemetry, not a tamper-proof security audit log; the activity events do not collect code answers, keystrokes, or private content. Students can create only events attributed to their own account, while administrators and owners can read the global activity collection.

Deploy the updated Firestore rules before using the dashboard against the hosted Firebase project:

```sh
npx firebase-tools deploy --only firestore:rules,firestore:indexes
```

The rules authorize administrator and owner reads using `user_roles/{uid}` (falling back to the legacy profile role where no role document exists) and do not allow users to change their own role. The index definitions support the dashboard's latest progress and assessment queries. New activity logging and dashboard reads will not work against the hosted project until the rules and indexes are deployed and the indexes finish building.

## Owner and Administrator Roles

Roles are managed server-side in `user_roles/{Firebase UID}`. Clients cannot read or write these documents. The Express backend verifies Firebase ID tokens and uses Firebase Admin credentials for role checks and updates. The `users/{uid}.role` field remains a read-only compatibility fallback for existing administrators when no `user_roles` document exists.

To bootstrap the first owner once:

1. Sign in to KielTech Academy with the Google account that should own the platform.
2. Find that account's Firebase UID in Firebase Authentication, then create `user_roles/{UID}` in Firestore with `role: "CEO & Founder"` (exact spelling and capitalization).
3. Deploy the updated Firestore rules and deploy the Express backend with its Firebase Admin service-account credentials.
4. Sign out and back in. The account menu should show **CEO & Founder**, and the owner can open **Manage admins** from the admin dashboard.

The owner-management page lists Google-linked Firebase Authentication accounts. It can grant or revoke only the `admin` role; it cannot assign, modify, or revoke `CEO & Founder`. The API rejects self-role changes and founder-target changes. Firestore rules check `user_roles` first and treat it as authoritative, so recording `role: "student"` there revokes a legacy admin role too. All role changes are made with the backend Admin SDK; browser clients remain denied access to `user_roles`.

This feature requires the Node/Express backend to be deployed and reachable at the same origin for `/api/account/role` and `/api/owner/*`. Its service account needs permission to read and write Firestore role documents and to look up/list Firebase Authentication users. Firebase Hosting by itself serves only static files and does not run these endpoints. Keep the service-account key private and provide it to the backend as a secret or protected file path, never as a frontend setting.
